FinLens Prompt Caching — Design Document
1. Where to Place cache_control Markers
Anthropic's prompt caching works by checkpointing the KV cache at a specific position in the input token stream. Everything up to and including the marked block is cached; everything after is treated as the dynamic portion sent fresh each call. For FinLens, the optimal structure is a two-layer approach.
Layer 1 — System prompt: Mark your system prompt with cache_control: {"type": "ephemeral"}. Your system prompt is identical across all five calls (role definition, output format instructions, etc.), so this is free money — a few hundred tokens cached for the session lifetime at essentially no cost.
Layer 2 — Filing text: This is where the real savings live. The filing content should be a document-type content block (or a text block if you're not using the document beta), placed after the system prompt but before the user question, and it should carry the second cache_control marker. The mental model is: system prompt → filing text → user question, where the cache boundary sits at the end of the filing text. The user question (e.g., "extract the income statement," "generate bear case") is tiny and varies per call, so it stays outside the cache. You can use up to four cache_control breakpoints per request; two is the right number here.
The ordering matters strictly. Anthropic matches the cache by comparing the prefix up to the marker byte-for-byte. If the system prompt or filing text changes at all between calls — even whitespace — you get a miss. Pin both to immutable strings the moment the filing is loaded.

2. Cache Lifecycle and TTL Strategy
The default ephemeral TTL is 5 minutes, extendable to 1 hour by passing the anthropic-beta: prompt-caching-2024-07-31 header (which you're presumably already using, or will need to add). For a typical FinLens session — five calls over 1–3 minutes — the 5-minute default is technically sufficient, but use the 1-hour TTL anyway, for two reasons.
First, users frequently pause between steps: they read the bull/bear output, open a browser tab, come back. A 5-minute window is surprisingly easy to blow past in practice. Second, the re-analyse button is your killer edge case. If a user hits re-analyse 7 minutes after the first run, a 5-minute TTL gives you a cold miss and you pay full input price again. The 1-hour TTL costs the same to set up (cache write price is identical regardless of TTL) and makes re-analysis essentially free for the entire working session.
Post-commercial, when multiple users may analyze the same filing, the 1-hour window also increases the probability that User B's session overlaps with User A's cached prefix — though cross-user cache sharing only applies when the exact same system prompt + filing text prefix is sent, which it will be if you canonicalize the filing text on ingest.

3. Cost Savings Math
Current Anthropic pricing for claude-sonnet-4-6: input tokens ~$3/M, cached read ~$0.30/M (roughly 10×). Cache write is ~$3.75/M (a modest surcharge on the first call that populates the cache).

Without caching: 4 Sonnet calls + 1 Haiku call × 100k tokens ≈ $0.30 + $0.08 = $0.38 in filing-token input costs (ignoring output and user-prompt tokens, which are small).
With caching: $0.375 (write) + $0.030 + $0.080 + $0.030 + $0.030 = $0.545 on the first session — actually slightly more, because the write surcharge is real. But on the re-analyse (second pass, same session): four hits at $0.030 + one Haiku hit at $0.008 = $0.128 vs. $0.38 uncached. That's a 66% reduction on re-analysis. For a commercial product where a filing might be analyzed dozens of times, caching pays for itself quickly.
The first-pass write surcharge is worth it as soon as users make even one re-analysis call — which the re-analyse button almost guarantees.

4. Monitoring Cache Hit Rate
Every Anthropic API response includes a usage object with four fields when caching is active: input_tokens, output_tokens, cache_creation_input_tokens, and cache_read_input_tokens. A hit shows cache_read_input_tokens > 0; a miss (or first write) shows cache_creation_input_tokens > 0.
Add a lightweight logging layer to claude_analyzer.py that captures these fields from every response and surfaces them in the Streamlit sidebar — you already have a cache count widget there, so this is a natural extension. Log at minimum: call name, model used, cache_read_input_tokens, cache_creation_input_tokens, and total input tokens. This lets you immediately see if a call that should be a hit is coming back as a miss.
The API does not currently expose a cache_miss_reason field (as of the prompt-caching beta), so when you get an unexpected miss, you'll need to debug by inspection. The most common causes are: (a) the filing text or system prompt differed by even one character, (b) the model was different from the call that wrote the cache, (c) the TTL expired, or (d) the cache_control block ordering changed. A useful debug tool: log len(filing_text) and a sha256(filing_text) hash at the start of each call — if the hash changes, you have a mutation bug, not a caching bug.

5. Edge Cases to Plan For
Filing text changes mid-session. This shouldn't happen in FinLens since you load the filing once and hold it in session state, but if it does (user uploads a revised PDF, or your MAX_FILING_CHARS truncation produces different output on retry), the cache is simply invalidated — Anthropic will write a new cache entry. No error is thrown; you just pay the write price again. Guard against this by freezing the filing string into session state as an immutable value at load time and never mutating it.
Model switch mid-session (Sonnet → Haiku for MD&A). This is your biggest structural edge case. Prompt caches are model-scoped — a cache written by Sonnet cannot be read by Haiku, and vice versa. This means your MD&A sentiment call (on Haiku) will always be a cache write, not a read, unless you've previously made a Haiku call against the same filing in the same session. The practical fix: if the Haiku call is always step 3, treat it as always writing its own cache entry. If you ever add a second Haiku call (e.g., a Haiku-based quick summary), that second call will hit the Haiku cache. Structure the call order deliberately: group all Sonnet calls together and all Haiku calls together to maximize same-model cache hits within each group.
Context window and token counting. At 100k filing tokens, you're well within Sonnet's 200k context window, but confirm your system prompt + filing + user question totals don't approach the limit. Also note that Anthropic requires a minimum of 1,024 tokens in a block before it's eligible for caching — your filing text comfortably clears this, but double-check your system prompt length if it's unusually short.

Code Structure Recommendation
In claude_analyzer.py, the architecture should treat the filing text as a session-level constant that's assembled once and reused across all call functions. Here's the structural pattern to implement:
Introduce a FilingContext dataclass (or a plain dict) that holds the pre-built message content — the system prompt string and the filing content block with cache_control already attached. This object is constructed once when the filing is loaded and passed into every analyzer function, rather than each function independently assembling the filing content.
System prompt: Move to a module-level constant and attach cache_control there. It should not be assembled inside any individual function.
Filing content block: Built once in a build_filing_context(filing_text: str) helper that returns the content list containing the document/text block with cache_control: {"type": "ephemeral"}. This helper is called at session load time, stored in st.session_state, and passed as a parameter to analyze_financials, analyze_summary, analyze_bear_bull, and analyze_mda_sentiment.
Each analyzer function receives the pre-built filing content block, appends its own user-question message, and makes the API call. No function should re-construct the filing content from raw text — that's the mutation risk you're guarding against.
Logging layer: Add a log_cache_usage(call_name: str, usage: dict) helper that extracts cache_read_input_tokens and cache_creation_input_tokens from the API response and writes them to a session-state list. Wire the sidebar cache count widget to this list so you get per-call visibility rather than a single aggregate count.
The analyze_mda_sentiment function (Haiku) should be explicitly documented in the code as "maintains its own cache, separate from Sonnet calls" so future contributors don't assume the Haiku call benefits from the Sonnet cache writes.
